## 1. Principles

- Additive only: no `DROP`, `RENAME`, `ALTER COLUMN`, `UPDATE`, `DELETE` or `INSERT` in the migration (checked mechanically, section 8).
- Every column added to an existing table is nullable or has a constant default.
- The Prisma client is **not** regenerated by this work (section 10).
- Same conventions as the existing schema: `String @id @default(uuid())`, `createdAt`/`updatedAt`, soft delete where records are user-managed.

## 5. What the migration SQL contains

**Part 1** is exactly what `prisma migrate diff` generates from the previous schema to the new one (embedded verbatim and re-checked after formatting: identical). **Part 2** adds what Prisma cannot express:

- partial unique index `QuestionOption_one_correct_per_question` (at most one correct option per question);
- extra composite foreign key `AttemptAnswer_option_belongs_to_question_fkey`;
- 11 CHECK constraints (drive code format and test window, candidate ranges, normalised application contact, template/section bounds, attempt deadline, feedback ratings, OTP counter).

The file is wrapped in `BEGIN; … COMMIT;`, so a failure leaves the schema unchanged.

## 6. Review of the integrity and isolation constraints

**Answers (composite foreign keys).** An answer row is identified by (`attemptId`,`questionId`). Two keys protect it:
1. (`attemptId`,`questionId`) must exist in `AttemptQuestion`: an answer can only be stored for a question on **that attempt's own generated paper**, and the key is the only way to refer to it, so one candidate's answer cannot land on another attempt.
2. (`questionId`,`selectedOptionId`) must exist in `QuestionOption`(`questionId`,`id`): the chosen option must belong to **the same question**. This closes a gap in my first proposal (an option of a different question could previously be selected). A NULL option (unanswered, marked for review) skips this check.
Deleting an attempt cascades to its paper and answers; deleting a question or option that appears in a paper or answer is blocked.
*Tested:* answer to a question not on the paper → rejected; option of another question → rejected; unanswered/marked answer → accepted; duplicate answer row → rejected; cascade on attempt delete → works.

**Application uniqueness.** One application per (drive, email) and per (drive, mobile), enforced by the database through lower-cased and normalised copies, plus unique `applicationNo`. A returning candidate therefore resumes rather than duplicates. The same person may apply to a different drive. *Tested:* duplicate email, duplicate mobile, same values in another drive (allowed), upper-case email and non-Indian mobile (rejected).

**Question-option correctness.** The partial unique index allows many wrong options but only one correct option per question; `(questionId, position)` prevents duplicate positions. *Tested:* second correct option rejected, extra wrong options accepted.

**Access isolation.**
| Role | What the database guarantees | What the API must enforce |
|---|---|---|
| Candidate | sessions are in `CandidateSession` (cannot be confused with staff `RefreshToken`); every candidate-owned row is reachable only through `candidateId`; answers cannot cross attempts | candidate token type; every candidate endpoint derives `candidateId` from the token, never from the request; never select `QuestionOption.isCorrect` |
| Coordinator | `DriveCoordinator` is the only link from a coordinator to a drive | filter every drive/application query by the caller's `DriveCoordinator` rows; never return scores |
| Interviewer | `InterviewPanelist` links an interviewer to an interview; `InterviewFeedback` requires a panel row | filter by panel membership; only the panelist writes their own feedback |
**Honest limits:** PostgreSQL row-level security is not used, so isolation relies on API checks backed by these keys. Cross-table consistency such as "the application's candidate equals the interview's candidate" or "`Application.email` equals the candidate's email" is application logic, not a constraint.

## 10. Important operational note: Prisma client sequencing

`prisma generate` was **not** run, so `backend/src/generated/prisma` and the running backend still use the old client. If the client were regenerated and the backend rebuilt and restarted **before** the real database is migrated, every query on the four changed tables would ask for columns the real database does not have and fail. Therefore: regenerate the client and rebuild only after the migration has been applied to the database that backend uses. Also, `prisma migrate dev` (not used here) would report drift for the hand-written CHECKs and partial index; use `migrate deploy`.
