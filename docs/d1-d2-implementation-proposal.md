### The schema change
```prisma
model TestTemplate {
  // existing fields ...
  drives DriveTemplate[]
  @@unique([level, name])   // existing

}

model DriveTemplate {
  driveId    String
  level      TestLevel
  templateId String
  assignedAt DateTime  @default(now())

  drive    Drive        @relation(fields: [driveId], references: [id], onDelete: Cascade)
  template TestTemplate @relation(fields: [templateId, level], references: [id, level], onDelete: Restrict, onUpdate: Restrict)

  @@id([driveId, level])
  @@index([templateId])
}
```

### Migration SQL (complete, 1 table + 1 index + 2 foreign keys)

### Design points
- **Prisma and PostgreSQL support the exact relation.** `prisma validate` accepts a composite relation in which `level` is both part of the primary key and part of the foreign key, with `onUpdate: Restrict`. The `level` column has the same enum type (`TestLevel`) on both sides. PostgreSQL requires a unique index on the referenced pair, which is the `TestTemplate_id_level_key` index in this migration.
- **Referential actions.** Drive deletion removes its mappings (`CASCADE`). A template referenced by a drive cannot be deleted (`ON DELETE RESTRICT`).
- **One deviation from the default, on purpose:** the template foreign key uses `ON UPDATE RESTRICT`, not Prisma's default `CASCADE`. With `CASCADE`, editing the level of a template that a drive uses would silently rewrite the mapping's `level` (part of the primary key) and move the template into a different slot. With `RESTRICT` the change is refused, which matches the rule "a template with consumers is not re-levelled".
- **What the database cannot enforce (backend rules to implement later):** a drive's rows must match `Drive.levelAllowed` (UG-only drive has only a UG row; BOTH has both); registration cannot open until every allowed level has a template; a template with attempts is read-only for structure; a mapping cannot be replaced after attempts exist for that drive and level.
- **Existing rows:** none are touched. The test database has 0 templates and 0 applications, so there is nothing to back-fill, and existing drives simply have no mappings yet.

## 2. D-1: `drives.viewAssigned` (proposal only: no files edited, nothing executed)

### Existing definitions (read-only inspection)
`backend/prisma/seed.ts` defines 19 permissions and per-role lists. `SUPER_ADMIN` receives **every** defined permission (`permissionDefinitions.map(...)`). `CAMPUS_COORDINATOR` has `candidates.viewAll`, `candidates.register`, `testStatus.monitor`. `HR_ADMIN` has `drives.manage`. The test database matches these lists exactly.

### Proposed catalogue entry and mappings
| Item | Value |
|---|---|
| Permission | `drives.viewAssigned`: "View recruitment drives assigned to the user" |
| CAMPUS_COORDINATOR | add (the point of the permission) |
| SUPER_ADMIN | add (keeps the seed invariant "SUPER_ADMIN holds every defined permission"); behaviourally redundant because SUPER_ADMIN has `drives.manage`, which resolves to ALL scope |
| HR_ADMIN | **no change**: keeps `drives.manage` (ALL scope) |
| INTERVIEWER, CANDIDATE | no change |

Scope resolver (to implement later, with the coordinator endpoints): `drives.manage` → ALL; else `drives.viewAssigned` → only drives with a `DriveCoordinator` row for the caller; else none. It never derives scope from `testStatus.monitor`, `candidates.viewAll` or `candidates.register`.

### Additive, idempotent data change (outline: not written, not run)

### The unsafe `seed.ts`, and how the new mapping survives it
`seed.ts` rebuilds each role's mappings from its own lists (`rolePermission.deleteMany` then `createMany`, not in a transaction). If it is ever re-run **before** it knows the new permission, it deletes the coordinator's and SUPER_ADMIN's `drives.viewAssigned` mappings. Therefore, in a separately approved change:
1. add the permission to `permissionDefinitions` (SUPER_ADMIN then receives it automatically) and `"drives.viewAssigned"` to `rolePermissions.CAMPUS_COORDINATOR`, in lockstep with the additive data change (proposed diff below);
2. until that change is approved and merged, **do not run `seed.ts`** against any database;
3. separately consider hardening it: wrap the mapping rebuild in a transaction, stop overwriting the demo college, add a database-target guard, and drop the default-password demo users.

### Drift test (future; design)
`seed.ts` runs its `main()` on import, so a test cannot import it. Either extract the permission/role data into a pure module (for example `prisma/seed-permissions.ts`) that `seed.ts` imports, or parse the file text. The test asserts:
- every permission string used in `requirePermission(...)` / `permissions.includes(...)` in `src/` exists in the catalogue;
- `drives.viewAssigned` is mapped to CAMPUS_COORDINATOR and SUPER_ADMIN and **not** to HR_ADMIN, INTERVIEWER or CANDIDATE;
- SUPER_ADMIN holds every catalogue permission;
- no role mapping references an unknown permission;
- the additive data script and `seed.ts` define the same set.
